# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Sanidad Teis": a class project (DIW, a front-end module) for a health centre. Vue 3 + Vite SPA with a small Express + Mongoose backend in the same repo. Management pages: patients (`XestionPaciente.vue`), doctors (`XestionDoctores.vue`) and appointments (`XestionCitas.vue`, model `Cita.js`, routes `/api/citas`; POST checks the patient's DNI (`pacienteDNI` in the cita, `dnipac` in Paciente) exists → 404). The student follows the teacher's pace, so keep changes scoped to what is asked and explain them; the user often wants the reasoning, not only the fix.

**Language:** the UI text and code comments are in **Galician** (e.g. "Gardar", "Limpar", `// baleira o formulario`). Write new comments in Galician to match. Some older comments and alert texts are in Spanish.

## Commands

```bash
docker compose up -d     # MongoDB 7 on :27017 (docker-compose.yml; credentials there and in .env MONGO_URI)
npm start                # Vite (:5173) + backend (node backend/server.js, :3000) via concurrently
npm run dev              # frontend only
npm run build            # production build → dist/ (quick way to catch template/compile errors)
npx eslint src           # lint (flat config in eslint.config.js); expect many formatting warnings, 0 errors
```

- There are **no automated tests**. Verify changes with `npm run build`, curl against `http://localhost:3000/api/...`, and the running app.
- The backend runs with plain `node` (no watch): **after any change under `backend/`, the server must be restarted** or it keeps serving the old code. This has caused "my fix doesn't work" confusion several times.
- Run commands from the repo root: `server.js` reads `./backend/data/*.json` with paths relative to the current directory.
- `.env` holds `MONGO_URI` (and `PORT`). Database `bbdd`, collections `pacientes`, `doctores` and `citas`.

## Architecture

**Frontend (`src/`)**
- `router/index.js`: one route per page component in `src/components/` (no `views/` folder). The catch-all `NotFound` route goes last.
- `api/*.js`: one axios module per resource. The base URL `http://localhost:3000/api` is hard-coded in each file (not read from `.env`). `getPacientes`/`getDoctores` sort by surname (`localeCompare`, "es") on the client.
- `utils/alertas.js`: SweetAlert2 helpers (`alertaExito`, `alertaError`, `alertaInfo`, `alertaConfirmacion`). `alertaConfirmacion` resolves to a Swal **result object**, so check `.isConfirmed`, never the object itself (an object is always truthy, so Cancel would still delete). Deletes use `alertaEliminar` instead (red "Eliminar" button, `focusCancel: true` so Enter/habit cancels).
- `store/` (Pinia, registered in `main.js`): `pacienteStore.js` (`usePacienteStore`: `dnipac`, `nomepac`, `apelpac`) and `doctorStore.js` (`useDoctorStore`: `_id`, `nomedoc`, `apeldoc`, `espedoc`). **Rule: selected for Citas = loaded in the Pacientes/Doctores form.** `cargarNoFormulario()` (used by ✏️, 🔍 and `recuperarSeleccionado`) selects; `limpiarFormpac()`/`limpiarFormdoc()` deselect, so saving, deleting the loaded record and 🧹 all clear the selection (saving does not select). Leaving a page destroys its form, so on mount `recuperarSeleccionado()` reloads the stored patient/doctor into the form. Pinia state is lost on a full reload (F5). The folder is `store/` (singular).
- `XestionCitas.vue`: row 1 (all read-only, one line on desktop) = ID cita (disabled), DNI paciente, Doctor (disabled input with the selected doctor's name, teacher's request) and ID doctor; DNI and ID are `RouterLink`s styled like fields (clicking opens Pacientes/Doctores, where the selected one is reloaded; "—" when none; `aria-labelledby` because a `<label for>` can't target a link), 🧹; row 2 = Data, Hora, Motivo, Tarifa (€), Estado; row 3 = Diagnóstico and Tratamiento textareas (side by side from `md`). These three fields (`tarifa` as `Double`, `diagnostico`, `tratamiento`) replaced `observacions` on purpose (student's choice); old citas still have `observacions` in the DB, it's just not shown. Tarifa is `step="0.01"`, right-aligned, shown as "25,00 €" in the table (`formatearTarifa`). Patient/doctor come only from the stores. The list (`citasLista`) shows the selected patient's citas under a centred heading "Citas de {name} ({DNI})" (patient name from the store; so the table has no Paciente column), with a hint when none is selected. Above the table, three checkboxes: "Mostrar todas as citas" in the middle (`mostrarTodas`: every cita in the system, heading "Todas as citas", plus a DNI paciente column via the computed `cabeceiras`; only the DNI because the cita doesn't store the name), "Ordenar por data" on the left (`ordenarPorData`: ticked = newest first by `fecha + hora`, unticked = oldest first; string comparison is safe because dates are ISO `YYYY-MM-DD`, also in the teacher's DB; a "Hoxe" divider row shown only when ticked is still to be added by the student) and "Mostrar as citas borradas" on the right (`mostrarBorradas`). 🧹 there clears both stores. Citas can be created, listed and edited: ✏️ (Accións column) loads the cita into the form (`editando`, its `_id` shown in ID cita), **selects the cita's own doctor** in `doctorStore` and, if the cita belongs to another patient (possible with `mostrarTodas`), **selects its patient** too (`getPacienteByDni`, because the cita only has the DNI; 404 → error, nothing loaded). Otherwise Gardar would move the cita to the previously selected patient. It asks `confirmarDescartar()` first and scrolls to the top (`window.scrollTo`, like Pacientes/Doctores). Loading is only through ✏️ (student's choice, no row click); Gardar then asks for confirmation and PUTs (`modifyCita`), with the same "Non hai cambios" / unsaved-changes (`copiaOrixinal`, `confirmarDescartar`) rules as the other pages. **Citas are never deleted** (teacher's rule: the data must be kept; only the `estado` changes; removal is done directly on the server). The doctor can't be changed while editing (going to Doctores destroys the Citas form). Past dates: `hoxe` is today as local `YYYY-MM-DD` (built with getFullYear/getMonth/getDate, not `toISOString`, which is UTC); `dataPasada` (computed) is true when `fecha < hoxe`, except while editing a cita whose date is unchanged (`dataOrixinal`), so old citas can still get their `estado` updated. It turns the Data field red (`:erro`), shows a `CaixaErros` message (`#data-erro`, `role="alert"`) inside the centred button block, and blocks Gardar via `motivoNonGardar`. New citas also get `:min="hoxe"` on the date input (no `min` while editing, or the browser's native validation would block saving a past cita). Browser-side only; the API doesn't check it. PDF button (after Limpiar, only while `editando`): `imprimirXustificante()` → `generarXustificante()` in `utils/pdf.js`, a one-cita slip to hand to the patient (Paciente, DNI, Doctor, Especialidade, Data, Hora, Motivo; **no** Tarifa/Diagnóstico/Tratamiento/Estado). Disabled while `haiCambiosSenGardar()` (visible hint `#axuda-pdf`), so the slip always matches the DB.
- `AxendaDia.vue` (`/axenda`): the citas of one day (date input, defaults to today; an emptied date goes back to today), a 5-day strip with the chosen day in the middle and its cita count (only the chosen day on phones), a table without `borrada` citas sorted by hour, and a PDF of that day (`generarPDF`).
- `VistaAcceso.vue` (`/acceso`): login **skeleton only, no authentication yet** (a real login needs users and hashed passwords in the backend). DNI/NIE (instead of a username, like the register page; format not validated yet) + Contrasinal (`autocomplete="username"`/`"current-password"`, 👁 show/hide with `aria-pressed`), "Lembrar a sesión", "Esqueciches o contrasinal?" (a link-styled button). Entrar and the forgotten-password button only show an `alertaInfo` "aínda non está dispoñible". "Novo usuario? Rexistra unha conta" (`RouterLink`) opens `VistaRexistro.vue` (`/rexistro`, not in the menu): also a skeleton, same narrow panel, DNI/NIE (teacher's request, instead of a username; `validarDocumento`, copied from Pacientes on purpose, teacher's choice) + Correo (required, for recovering a forgotten password; `validarCorreo` copied from Pacientes but required: empty doesn't change the flag; uniqueness can't be checked until there is a users backend) + Contrasinal (at least 6 characters, `contrasinalNonValido`) + Repetir contrasinal (`autocomplete="new-password"`, one 👁 toggles both; must match, `nonCoinciden`). Each error follows the usual blur/input rules and sits in one `CaixaErros` (`#dni-erro`, `#correo-erro`, `#contrasinal-erro`, `#repetir-erro`); `rexistrar()` re-runs every check (Enter skips `@blur`), then Crear conta shows an `alertaInfo`. Acceso and Rexistro have no red `*` (every field is required; exception noted in `GUIA-ESTILO.md`, inputs keep `required`); "Xa tes conta? Accede" goes back. The menu link is the last item at the right end of `NavBar.vue`: a `CircleUserRound` icon, with the text "Acceso" visible on phones and `md:sr-only` on desktop.
- Management pages follow the same structure: a `reactive` form object (`novoPaciente` / `novoDoctor`), an `editando` ref, validation-flag refs, and functions grouped under comment headers ("Zona de declaracións", "ciclo de vida", "métodos", "funcións auxiliares"), each with a one-line comment.

**Backend (`backend/`)**
- `server.js`: Express app; mounts `rutas/pacientes.rutas.js`, `rutas/doctores.rutas.js` and `rutas/citas.rutas.js`, and serves `/api/municipios`, `/api/especialidades` and `/api/tarifas` straight from the JSON files in `backend/data/`.
- `modelos/*.js`: Mongoose schemas with explicit `collection` names. Field names use a suffix per entity: `…pac` for patients (`dnipac`, `nomepac`, `apelpac`, `movilpac`, `propac`, `munipac`, `lopdpac`…) and `…doc` for doctors (`nomedoc`, `apeldoc`, `coledoc`, `movildoc`, `maildoc`, `espedoc`). Citas use plain names (`pacienteDNI`, `doctorId`, `fecha`, `hora`, `motivo`, `tarifa`, `diagnostico`, `tratamiento`, `estado`).

### How each entity is identified (they differ on purpose)

| | Patients | Doctors |
|---|---|---|
| Key | `dnipac` (DNI/NIE) | MongoDB `_id` |
| API | `/api/pacientes/:dni` (GET/PUT/DELETE) | `/api/doctores/:id` (PUT/DELETE), `findById…` |
| Citas link | `cita.pacienteDNI` (plain String, no `ref`; named like the teacher's model so his DB loads) | `cita.doctorId` (`ObjectId`, `ref: "Doctor"`, populated in `GET /api/citas`) |
| On load into form (✏️/🔍) | `delete novoPaciente._id` | **keep** `_id`; it is what `modifyDoctor` uses |
| On clear (`limpiarForm…`) | fields reset to `""`/`false` | also `delete novoDoctor._id` (an `_id: ""` breaks the next POST) |
| Create | POST checks the DNI and returns 409 if it already exists; POST and PUT also return 409 if another patient has the same `movilpac` (teacher's rule; PUT excludes itself with `dnipac: { $ne }`). Each 409 body has `campo` (`dnipac`/`movilpac`) so the form shows the right alert; for the phone it keeps the data and focuses `#telefono` | POST/PUT return 409 only if **every** field equals another doctor's (`datosDoctor`; PUT excludes itself with `_id: { $ne }`) |

- PUT routes `delete req.body.dnipac`/`_id` so the identifier can't be changed through the body; the form also disables the DNI field (`:disabled="editando"`) while editing.
- The old unique index `iddoc_1` was dropped from `doctores` when doctors switched to `_id`. Removing a `unique` field from a schema does **not** drop its index; drop it manually or every save fails with E11000 on `null`.

### Form behaviour to preserve (both pages mirror each other; doctors have no 🔍, the filter replaces it)
- Field validation ("punish late, reward early"): the error appears on `@blur`; while it is shown, `@input` re-validates so it disappears as soon as the value is correct. **Never erase the user's value**; only normalise it (upper case, trim) once it is valid. Required fields (DNI, phone): an empty value doesn't change the flag (untouched fields aren't marked, a visible error persists until fixed). Optional fields (email): empty clears the error. Error messages sit together above Gardar (`.erros`), each with a valid example, and keep their `id` for the inputs' `aria-describedby`. Gardar is disabled while the computed `motivoNonGardar` is non-empty (errors shown, or missing required fields / privacy checkbox); that text is a hover tooltip (wrapping `span.group`, `pointer-fine:group-hover:block`; the disabled button has `disabled:pointer-events-none`) and also a `<p id="axuda-gardar">` under the buttons, visible unless there's a mouse (`pointer-fine:hidden`), referenced by `aria-describedby`. Headless Chrome reports `pointer: none` and can't emulate a mouse, so the tooltip can only be checked manually.
- `guardarPaciente` re-runs `validarDocumento()`/`validarCorreo()`/`validarTelefono()` before saving, because pressing Enter submits without firing `@blur`. 🔍 also validates the DNI before searching.
- On success it calls `limpiarFormpac()`; on error the form keeps its data.
- Changing province resets `munipac` in the `@change` (not inside `cargarMunicipios`, which ✏️/🔍 also call and must keep the saved municipality).
- 🔍 is disabled while editing; a 404 on search sets `editando = false`.
- Button row under the form: Gardar, then a secondary "Limpiar" button (same action as 🧹, which also stays at the top), then "Eliminar". All three are equally spaced (`gap-3` on phones, `md:gap-4`; teacher's request, the old `md:ml-10`/`mt-4` separation was removed); an accidental click is harmless because `alertaEliminar` has Cancelar focused. Eliminar only shows when `editando`. Deleting the patient loaded in the form clears it.
- Alerts (SweetAlert, texts in Galician): an action that first asks "Seguro que…?" (delete, modify) shows **no success message** afterwards, only an error if it fails; creating a new patient (no question) shows success. Loading a record (✏️/🔍) shows no popup. Backend 409 → specific "Xa existe…" message. Failing to load the list (`cargarPacientes`) or provinces shows an error.
- Unsaved data: `copiaOrixinal` holds a snapshot (`fotoFormulario()`) of the loaded patient; `haiCambiosSenGardar()` compares against it (or, for a new form, checks for any typed field except the privacy checkbox). 🧹 (`limparConConfirmacion`) and 🔍 call `confirmarDescartar()` first (🔍 ignores the DNI itself); ✏️ calls it only when `editando` (`editando.value && !(await confirmarDescartar())`), so filter text never triggers the question. Gardar on an unchanged loaded patient shows "Non hai cambios que gardar". `limpiarFormpac()` itself never asks (it's also used after save/delete). Leaving the page with unsaved data is not guarded.
- Filter: while not `editando`, the form doubles as a filter. `pacientesFiltrados` keeps patients where every filled `CAMPOS_FILTRO` field is *contained* in theirs, ignoring case and accents (`normalizar`). The table iterates `pacientesFiltrados`, so row actions must use `pacientes.indexOf(p)`, not the row `index`. Known side effects: typed filter text counts as unsaved data for 🧹 (✏️ doesn't ask: the clicked row always matches the filter, so nothing is lost except the privacy checkbox), and partial DNI/phone get marked invalid on blur.
- PDF: `utils/pdf.js` `generarPDF(titulo, cabeceiras, filas, subtitulo)` (jsPDF + jspdf-autotable, palette green header) opens the PDF in a new tab via `window.open(doc.output("bloburl"))` (must run inside the click handler or popup blockers interfere; the tab has no real filename). Patients export only DNI, Apelido, Nome, Teléfono (privacy) of the filtered list.
- `gardando` locks Gardar/Eliminar while a save or delete request is in progress (prevents double submissions when the DB is slow or reconnecting); `motivoNonGardar` then reads "Gardando…".
- Doctors: `coledoc` starts as `null` (no radio checked) so Colexiado must be chosen and an empty value doesn't filter; `limpiarFormdoc` resets it to `null` and deletes every non-`CAMPOS` key (`_id`, `__v`). The doctors PDF leaves out the MongoDB `_id`.
- `Object.assign(form, record)` leaves extra keys (`_id`, `__v`) and keeps old values for keys the record doesn't have. Account for that when loading or clearing.

## Styling conventions
- **Tailwind CSS v4, utility classes only** (`@tailwindcss/vite`; config lives in CSS, no `tailwind.config.js`). No component has a `<style>` block. **`GUIA-ESTILO.md` is the reference** for every value (colours, text sizes, spacing, radii, component specs, mobile rules, accessibility).
- `src/style.css` (~60 lines): `@import "tailwindcss"`, an `@theme` with the palette as Galician-named tokens (`acento`, `acento-escuro`, `titulo`, `banda`, `acento-claro`, `foco`, `acento-suave`, `fondo`, `texto`, `perigo`, `perigo-suave`, `borde`, `desactivado`, `texto-desactivado` → classes like `bg-acento`, `text-titulo`), and **Tailwind's default colours are switched off** (`--color-*: initial`; only `white`/`black` re-added). Plus a `@layer base` with the background image, text/link colours and the focus outline. Colours used outside CSS must be updated by hand: `utils/pdf.js` (`VERDE` RGB) and `utils/alertas.js` (`confirmButtonColor`).
- Shared UI components in `src/components/comun/`: `BotonAccion` (variants `principal`/`secundario`/`perigo`/`icona`/`icona-perigo`; `to` → `RouterLink` styled as a button), `TarxetaPanel` (white panel), `TituloSeccion` (green band + `#accion` slot), `CampoFormulario` (label above + field classes via `v-slot="{ clases }"`), `CaixaErros`. Icons: `lucide-vue-next`, imported per icon, `aria-hidden` with the button carrying the `aria-label`.
- **Mobile first:** unprefixed classes are for phones, `md:` (768 px+) for desktop. Phones: one field per row, full-width 44 px buttons, ☰ menu, tables scroll inside an `overflow-x-auto` box. Page width max 1280 px (`max-w-7xl` in `App.vue`).
- Menu and footer (teacher's request): from `md` they are `sticky` (`top-0` / `bottom-0`, `z-20`, above the Gardar tooltip's `z-10`) and the page scrolls underneath; on phones they scroll with the page as before. The window still scrolls (no inner scroll container), so `window.scrollTo` keeps working. `App.vue` keeps its `py-4` on purpose (student's choice): the 16 px gap above the menu scrolls away before it sticks, and the footer lifts 16 px at the very end. The page sits in `<main class="md:flex-1">`, so on short pages the footer is at the bottom of the screen. `index.html` has `md:scroll-pt-16 md:scroll-pb-14` on `<html>` so Tab/`scrollIntoView` don't leave focused elements hidden behind the menu or footer.
- Form pages: the page panel has `rounded-t-none` (flush with the menu); labels above fields; fixed-format fields have fixed `md:w-*` widths, text fields `md:flex-1`; Gardar/Limpiar/Eliminar are `md:w-27`, equally spaced (`md:gap-4`, also on Citas). No "campo obrigatorio" note (the red `*` plus the Gardar hint explain it; inputs have `required`).
- Inicio starts with a decorative video (`h-[60vh]`, page-content width, no text on it) and the welcome card below. Files: `public/video/inicio.webm` + `.mp4` + poster (~1–1.4 MB, 1280×720, 18 s loop, no audio; sources/license in `public/video/CREDITOS.txt`, credit in the `figcaption` on a light chip). It starts from the script (no `autoplay` attribute) only if `prefers-reduced-motion` is not set, has a ⏸/▶ button (WCAG 2.2.2), `preload="none"` and `aria-hidden`. Self-hosted on purpose (a YouTube embed would need cookie consent).
- Servicios médicos (`ServiciosMedicos.vue`, data in `src/data/servizos.js` with an `imaxe` path per service): 6 image cards (1 column on phones, 3 from `md`). Clicking a card opens its details panel under that card's row; clicking it again or ✕ closes it (✕ returns focus to the card); nothing is open on arrival. The open panel shows "A partir de X €" on the Pedir cita line, right-aligned (not on the card): the page loads `/api/tarifas` (`backend/data/tarifas.json`) on mount and `prezoDesde()` takes the lowest `prezo` among the ids in the service's `tarifas` array (linked by id because the names differ; Informe médico, id 3, is left out on purpose since it's paid on top of a consulta). If the request fails or a service has no ids (Receta for now), the price line is simply hidden, with no alert (student's choice). Hover: bigger shadow + 4 px lift (`motion-safe:` only). In the panel, "Incluye" is 3 `acento-suave` tiles with a ✓ (3 across from `md`; every service has exactly 3 items). The panel is placed in the DOM right after the clicked card with `col-span-full`, and `grid-flow-row-dense` lets the rest of the row fill in first (so Tab order goes card → details → rest of row; accepted on purpose). Photos: `public/img/servizos/*.webp` (600 px, Unsplash License, credits in `CREDITOS.txt`), `alt=""` because the button text names the service.
- Alignment (teacher's rule): text left, numbers/DNI/IDs/dates/phones `text-center`, future amounts `text-right tabular-nums`.
- Tailwind pitfalls seen here: two utilities setting the same property on one element don't override by order in the class list (use a more specific variant, e.g. `[&.router-link-active]:border-acento-claro`); never build class names by concatenation (Tailwind only generates full class strings it finds in the source); `hover:` and `pointer-fine:` don't apply in headless Chrome (`pointer: none`), so hover styles can only be checked by hand.
